## Constats

### C1 — FAIBLE : trois tests e2e verrouillent l'ancien contrat « création BR admin-only », divergent du contrat réel A7 — suite rouge à l'exécution

La décision produit A7 du 25/10/2026 (audit-2) est appliquée aux deux
bouts : le serveur (`br-engine.mjs:268-276` — « tout joueur authentifié
peut creer le sien et l'arbitrer par defaut » ; `:330-339` — l'arbitre
désigné est tout compte existant, défaut le créateur) et le front
(`BrPage.tsx:275-277` — le panneau de création est rendu à tout
utilisateur connecté, commentaire « volontariat A7 »). Mais l'e2e verrouille
encore l'ANCIEN contrat :

- `br.spec.ts:95-102` (« refuse la creation a un non-administrateur ») :
  attend 403 — le serveur répondra 201 (création réussie). ROUGE.
- `br.spec.ts:104-110` (« refuse un non-admin ») : DOUBLON du précédent,
  même attente 403. ROUGE.
- `ui/br.spec.ts:94-101` (« le formulaire de creation est reserve a
  l'admin ») : attend `getByRole('button', { name: /Creer un salon BR/i
  }).toHaveCount(0)` pour un joueur — le bouton est rendu
  (`BrLobbyCreatePanel.tsx:184`, panneau visible pour tout connecté). ROUGE.
- `br.spec.ts:163-170` (« refuse un arbitre qui n'est pas
  administrateur ») : passe PAR COÏNCIDENCE — `arbiterId: 'quelquun'` est
  refusé parce que le compte n'existe pas (`INVALID_ARBITER`,
  `br-engine.mjs:334-338`), pas parce qu'il n'est pas admin : le libellé
  du test ment sur la règle réelle.

La suite n'est pas exécutée en CI (`playwright.config.ts:27` documente
l'absence de Playwright en CI) : ces rouges sont invisibles — exactement
la famille « l'E2E ne testait plus rien — en silence » que la config
avait déjà corrigée pour les tokens. Un `pnpm test:e2e` local renverrait
3 échecs sans rapport avec une régression. Piste : réécrire ces 3 tests
sur le contrat A7 (création acceptée à un joueur simple, arbitre désigné
quelconque existant, garde réelle = `requireLobbyArbiter`) — la docstring
front l'a déjà fait (constat C14 P13), l'e2e reste en retard.

### C2 — FAIBLE : `accessibility.spec.ts:23` — la route `/selection-mode` n'existe pas, le test axe analyse la page 404

la page rendue est bien la sélection, par exemple via son titre).

### C6 — INFO : `match.spec.ts:296-298` verrouille le contrat « salle jamais livrée » que le correctif C2 P13 devra changer

du contrat actuel, mais il FAIT PARTIE du contrat à faire évoluer :
le correctif de C2 (dérogation arbitre/participants) devra mettre à
jour cette assertion — sinon le test redeviendra rouge au bon fix.
INFO : mémoire de correction, pas un défaut.

## Résumé

Quatre FAIBLE, trois INFO. Le fil rouge : l'e2e est en retard sur les
décisions produit récentes — trois tests verrouillent encore la création
BR admin-only, contredite des deux bouts (serveur A7 + front A7), donc
rouges à l'exécution sans que la CI les voie ; le test axe analyse une
route fantôme (`/selection-mode`) ; et la famille « assertions vides »
de `auth-flow.spec.ts` ferait passer une validation ou une garde de
route morte pour couverte. Un mojibake irrécupérable dans
`admin-reports.spec.ts` complète le tableau. Les INFO : aucune couverture
push ni socket (cohérent avec le MAJEUR P9), l'assertion salle de
`match.spec.ts` fera partie du correctif C2 P13, et une collection de
duplicités/typos. Tout le reste est d'une qualité remarquable : le
harness (contextes isolés, TOTP réel, cache one-shot, aucun backdoor de
financement), les cycles de vie complets match/BR par HTTP avec
anti-fuite exhaustif, les gardes wallet exhaustives et atomiques, la
séparation revenue/arbiterPayouts, l'honnêteté sur la portée du mode
mémoire, l'avertissement double-frais UI vérifié jusqu'à la persistance
de la préférence, et les live specs à garde-fou de production avec
compte jetable auto-supprimé.
